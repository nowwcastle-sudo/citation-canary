# Citation Canary 로컬 검토 작업공간 설계

- 상태: 로컬 우선 방향 선택 완료, 상세 설계 검토용
- 기준 코드: 63cdcd3956135b1a02862fd2280745e4f002a110
- 목표: 추출 결과를 읽고 사람이 처분을 기록하며 관련 버전과 비교한다.
- HWPX 자동 수정, 법적 판정, 문서 업로드·원천 대량 수집은 계속 제외한다.

## 1. 호환성과 구성

기존 scan_document와 scan/demo CLI, schema-1 ScanReport를 유지한다.
새 작업은 별도 review, compare, render 명령으로 분리한다. Python 3.11+
표준 라이브러리만 쓰고 서버·데이터베이스·외부 런타임 의존성은 추가하지
않는다. 기존 스캔 출력에 시간 측정이나 사람 처분을 끼워 넣지 않는다.

## 2. 기능과 수용 조건

| ID | 기능 | 완료로 인정할 행동 |
|---|---|---|
| CC-L01 | 사람 처분 | 보고서와 1부터 시작하는 항목 번호를 명시해 confirm/reject/investigate/defer 중 하나를 기록한다. 스캔 상태값은 바꾸지 않는다. |
| CC-L02 | 처분 이력 | 같은 항목의 처분을 바꿔도 이전 사건을 보존하고 최신 처분을 구분한다. 손상·충돌·다른 보고서 결합은 거절한다. |
| CC-L03 | 보고서 비교 | 추가·삭제·상태 변화·근거 변화·기준일/카탈로그 차이를 구분한다. 애매한 인용 대응을 확정하지 않는다. |
| CC-L04 | 로컬 열람 보고서 | REVIEW/UNKNOWN 우선 보기, 전체 상태·미처분 집계, 근거와 최신 처분을 정적 HTML로 보여준다. |
| CC-L05 | 검토 측정 | 명시적으로 기록한 검토 시작/완료와 단계별 시간·처분 집계를 별도 기록한다. 스캔 JSON의 결정성은 유지한다. |

## 3. 별도 검토 기록

기록은 citation-review/1 형식의 별도 JSON이다. 입력 보고서를 canonical
JSON으로 직렬화한 SHA-256, document/catalog 해시, 기준일과 결합한다.
항목 키는 report_digest와 item_number의 쌍이다. locator 단독 키는
사용하지 않는다. 한 XML 노드에 서로 다른 인용이 여러 개 있을 수 있다.

사건에는 순번, 항목 번호, 처분, UTC 기록 시각, 이전 사건의 digest가
있다. 이는 변경·손상을 발견하기 위한 연결이며 작성자 인증이나 법적
감사 서명은 아니다. 초기 구현에서는 실명·원문·자유 메모를 수집하지
않는다. 최신값을 보여줄 때도 사건 이력은 삭제하지 않는다.

기존 기록 갱신은 명시적 review 명령에서만 허용한다. 전체 schema와
보고서 결합을 확인하고 동시 쓰기를 차단한다. 임시 파일의 완전한 쓰기
후 원자적으로 반영하며 실패 시 기존 기록과 실패 산출물을 보존한다.
읽기 전용 render/compare는 기록을 갱신하지 않는다.

시간 집계는 기록된 시작·완료 쌍만 사용한다. 시작/완료 누락, 시각 역전,
중복 구간은 측정 불가로 남기며 추정 시간이나 속도 개선율을 만들지 않는다.

## 4. 비교 규칙

동일 문서 해시의 보고서는 항목 위치와 인용 식별로 비교한다. 문서
해시가 다르면 제목·조문 식별이 양쪽에서 유일한 경우만 후보 대응으로
표시하고, 같은 문서의 후속 버전이라는 사실은 사용자 제공 관계로 남긴다.
중복·이동·여러 후보는 대응 확인 필요다. 처분은 새 보고서로 자동 승계하지
않는다. 카탈로그만 바뀐 일을 HWPX 수정으로 표시하지 않는다.

비교 대상은 각각 검증 가능한 schema-1 보고서다. collection_errors가
있는 보고서로 이전 항목이 해결되었다고 결론 내리지 않는다. 구분할 수
없는 변화는 unknown이며 빈 결과를 법적 검토 완료로 해석하지 않는다.

## 5. 로컬 화면과 입출력

HTML은 표·링크·정렬된 절을 가진 읽기 전용 파일이다. 외부 JS·폰트·이미지,
자동 조회, 브라우저의 원본 파일 접근을 넣지 않는다. 모든 값은 escape하고
원천 링크는 HTTPS로 제한한다. 사용자가 링크를 클릭하는 행위는 별도다.
화면에서 보이는 항목 번호를 review 명령에 사용할 수 있도록 표시한다.

화면에는 오류·빈 결과·미처분·처분 완료를 구분한다. 카탈로그에 근거가
있다는 표시를 원천 서버가 지금 사용 가능하다는 뜻으로 바꾸지 않는다.
출력은 명시한 로컬 경로에만 쓴다. 원본 보고서·HWPX·카탈로그와 같은
파일이나 하드링크, symlink/reparse 대상에는 쓰지 않는다.

새 입력 JSON은 파일당 8 MiB, 보고서당 10000항목, 검토 사건 50000개로
제한한다. 중복 키·NaN/Infinity·알 수 없는 schema·잘못된 index/enum은
거절한다. 실패 시 부분적 성공 화면이나 새 처분을 남기지 않는다.
HTML 파일은 기존 파일을 덮어쓰지 않는 것이 기본이다.

## 6. 검증 기준

동일 locator의 서로 다른 항목, 처분 두 번과 이력 보존, 잘못된 보고서
결합, 동시 갱신, 중단된 쓰기, 손상/대용량/중복 키 입력을 검증한다.
비교에는 동일 보고서, 카탈로그만 변경, 기준일 변경, 추가·삭제·중복·이동,
수집 오류가 있는 반대편을 포함한다. HTML 주입·민감정보·출력 충돌도
검증한다. 원본 bytes와 기존 스캔 출력의 결정성을 대조한다.

기존 전체 unittest와 zipapp 검증을 재실행한다. 새 runtime 모듈은
zipapp의 정확한 source/member allowlist에 명시적으로 추가한다. 기존
릴리스의 11-entry 계약과 새로운 후보의 구성 수를 섞지 않는다.
각 CC-L 요구를 구현·테스트·실행 결과와 연결해 공개 명세를 갱신한다.

## 7. 외부 연동 전환 조건

로컬 작업공간을 완성해도 공식 원천의 자동 수집·현재 가용성 확인은
구현 완료로 주장할 수 없다. 이 기능이 실제 병목이면 별도 카탈로그
갱신 명령을 설계하고 공식 API/다운로드 조건·인증·식별자·시행일/연혁을
확인한다. HWPX 본문이나 로컬 경로는 전송하지 않고 공개 인용 식별자만
사용한다. 실패하면 기존 카탈로그를 보존하며 모의 API만으로 연동 통과를
선언하지 않는다. 이 전환이 사용자 선택의 2단계다.
